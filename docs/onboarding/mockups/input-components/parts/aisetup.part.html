AI provider setup

Whether AI features run at all, whether your words leave this Mac, and which model answers — decided by a connection that has to prove itself before it counts.

States you can drive

Nothing here talks to a network. A deterministic fake table decides reachability: a key containing reject is refused 401, a host that is not in the table refuses the connection, and the scan only answers on ports something is actually listening on.

What this replaces

  • ChangeSettingsScreen.svelte:448 — the bare AI switch. Becomes the outcome of connecting, not the entry point: nothing is asked until the user answers "later" or "now".
  • :463–471 / :483–492 — the two rows of + kind buttons (one per local kind, one per cloud kind). Deleted. A single grouped selector plus Scan this Mac replaces eight buttons that all did the same thing: append an empty, unverified row.
  • :516 base URL, :525/:539 key field + Save key — the Save button goes. Reaching the provider is the save: the key is sent, the model list comes back, and the list is the receipt. A key that cannot list models never becomes a saved provider.
  • :553 the local endpoint field — demoted to the fallback under the scan. Typing a port is for the engine on another machine, not for the one already running here.
  • :570 ModelPickerMenu — the merged menu stays as the readout, but the chips inside each live card are the selection surface, so a model that was not in the last live listing is not offerable.

Backend change this design requires

This component's readiness rule is stricter than production: a default model counts only if its provider verified live and that live listing still contains that exact model id. Today the app can finish onboarding with AI enabled and no working model, which lands straight on the known bug where a job against an absent model dies in about six minutes and is never retried. Four call sites:

  • onboarding-ai.svelte.ts:144–157 — aiConfigMissing treats a cloud provider as configured once a string was written to the keychain. No validity check at all, and non-cloud kinds get no endpoint check either. Needs to read a verification result, not key presence.
  • :189–193 — aiUnverifiedNote ("Key saved but unverified") already knows the truth and is deliberately only a hint. Promote it: unverified must fail aiConfigReady, not annotate it.
  • ChangeSettingsScreen.svelte:182 — aiBlocked reads that same soft readiness, so the one hard gate in onboarding is gated on an untested key.
  • :188–192 — the $effect auto-enables the feature on the false→true readiness transition. Auto-enabling on an unverified provider is how the user ends up with AI on and nothing behind it. Keep the auto-enable, but fire it off verified readiness only.
  • syncFromSettings (:114–124) — restores a persisted default model without checking it still exists in any live pool. A model the provider dropped (renamed, deprecated, unpulled locally) survives a reload as a valid-looking default. It must be re-validated against the fetched pool and cleared with a visible reason when it is gone.

Concretely: one verify_ai_provider(id) → { models: [], latency_ms } command that lists models with the key the vault holds, called on connect and on Test; readiness derived from its result plus a membership check of the chosen model id. The frontend never needs the key back.

Secret handling

The key field is type="password", autocomplete="off", data-1p-ignore, data-lpignore, and has no value attribute — the demo buttons assign the input property. The string is read once, sent, and the field is cleared; state keeps a boolean, never the text. Nothing renders it, so it never reaches markup, an aria-label, a title, or a URL.
